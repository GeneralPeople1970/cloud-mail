# Cloudflare Workers Builds 绑定同步

控制台的“更新您的 Wrangler 配置以应用这些更改，确保部署保持同步”提示要求将资源绑定纳入部署配置。只在控制台添加 D1/KV，随后使用未声明这些绑定的 `wrangler.toml` 部署，可能移除绑定并导致接口报数据库未绑定。

`keep_vars = true` 保留控制台的运行时变量，不负责保留 D1/KV 资源绑定。部署入口同时传入 `--keep-vars`，避免源配置同步时遗漏该字段而清空运行时变量。

## 与上游的差异及同步要求

2026-11-06 核对上游 `main`（`d115f4c`）：D1/KV 配置仍为注释模板，上游没有 `deploy:builds` 入口及本文件所述的构建变量注入方案。这是本 fork 的部署保护，后续同步上游必须保留。

合并时保留 `scripts/deploy-builds.mjs`、`package.json` 中的 `deploy:builds`、临时配置的 Git 忽略规则、`wrangler.toml` 的变量保留设置及相关文档。不要用上游的注释模板替换实际构建入口，不要将控制台部署命令退回到未包含绑定的 `npx wrangler deploy` 或 `pnpm run deploy`。

构建设置中的资源 ID、线上 `db`/`kv` 绑定和运行时变量不能因上游没有对应值而删除。资源 ID 缺失时中止部署，不创建新资源替代旧资源，不清空已有数据。只有上游提供等效的保护后，才可在确认行为一致的基础上替换本实现，并更新 [项目说明](SKILL.MD)。

## Workers Builds 设置

本仓库提供 `pnpm run deploy:builds`，从构建环境变量读取现有资源 ID，将 `db` 和 `kv` 绑定加入临时 Wrangler 配置后部署。真实资源 ID 不写入 Git；原有 `wrangler.toml` 和运行时变量保持原有管理方式。

切换时，先进入 Worker 的设置 → 构建，配置并保存以下值，再推送包含脚本的提交到构建分支，避免推送立即触发旧部署命令：

| 项目 | 值 |
| --- | --- |
| 根目录 | `mail-worker` |
| 部署命令 | `pnpm run deploy:builds` |
| 构建变量 `D1_DATABASE_ID` | 已有 D1 数据库的 ID |
| 构建变量 `KV_NAMESPACE_ID` | 已有 KV 命名空间的 ID |

切换后不要重试尚未包含脚本的旧提交；旧提交会因找不到 `deploy:builds` 而失败，不能为了绕过该错误改回无绑定的部署命令。新提交部署成功后，在控制台的绑定列表确认 `db`、`kv` 指向已有资源，再检查网站配置接口。

保持已有依赖安装和构建命令。Wrangler 的 `[build]` 已负责打包前端，不需要重复添加前端构建步骤。

这两个变量属于 **Workers Builds 构建环境变量**，应配置在构建设置中；Worker 的运行时变量无法供该脚本读取。生产构建和非生产构建分别配置需要使用的资源 ID。

脚本在部署前检查两个 ID；缺失、格式不正确或源配置已经声明 D1/KV 时，会直接失败，避免上传缺少绑定或重复绑定的配置。该命令不接受额外参数，避免参数被忽略或覆盖绑定配置。临时配置位于 `mail-worker` 目录以保留相对路径，已被 Git 忽略，并在命令正常结束或部署返回失败后删除。

请使用现有资源，不要为了同步绑定新建数据库、清空数据或重新初始化数据库。该部署入口不执行数据库初始化或迁移。

## 其他部署方式

已经在本地专用 Wrangler 配置中设置资源绑定的部署，继续使用现有 Wrangler 命令。默认 `pnpm run deploy` 不变。

GitHub Actions 继续使用 `wrangler-action.toml` 及其现有环境变量替换流程，不受此入口影响。
